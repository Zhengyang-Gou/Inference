大语言模型推理通常可以划分为两个阶段：Prefill 阶段负责处理用户输入并生成 KV Cache，Decode 阶段则利用这些缓存逐步生成输出内容。传统推理系统通常将两个阶段部署在同一组 GPU 上，但二者的计算特征差异较大，容易产生资源竞争。P/D 解耦架构将 Prefill 和 Decode 部署在不同实例上，使两类资源能够独立配置和扩展，因此逐渐成为分布式大模型推理的重要架构。

P/D 解耦也带来了新的调度问题。一个请求到达后，系统不仅要选择执行 Prefill 的节点，还要选择后续执行 Decode 的节点，并将生成的 KV Cache 从 Prefill 节点传输到 Decode 节点。不同节点可能位于同一服务器、同一机架或不同机架，网络带宽和拥塞状态也可能随时间变化。因此，即使某个节点计算负载较低，如果它距离 Prefill 节点较远，KV Cache 的传输时间仍可能显著增加用户看到首个输出 token 的等待时间。

与此同时，LLM 推理请求之间经常存在相同或相似的输入前缀，例如共享系统提示词、文档背景或多轮对话历史。如果某个实例已经缓存了相关前缀的 KV Cache，将请求路由到该实例可以避免重复计算。不过，过度追求缓存命中也可能造成热点：大量具有相同前缀的请求会集中到少数实例，使这些实例排队严重，而其他实例处于空闲状态。由此可见，缓存命中率、计算负载和网络代价之间往往存在冲突。

在请求到达时，综合考虑 Prefill 和 Decode 实例的实时负载、请求能够复用的 KV Cache、节点之间的拓扑位置以及网络拥塞情况，联合选择合适的 Prefill 和 Decode 实例，而不是只按照单一因素进行路由。系统还可以根据实际情况判断，是采用标准的 P/D 解耦执行方式，还是直接在 Decode 节点完成较短请求的 Prefill，以避免不必要的跨节点 KV Cache 传输。

目标不是单纯提高缓存命中率或降低平均网络流量，而是降低首 token 时延和后续 token 生成时延，减少高负载和突发流量下的服务等级目标违约，并提高整个 GPU 集群的有效吞吐能力。研究重点主要位于推理系统的控制面，包括请求路由、实例选择、网络状态感知和在线负载调节。

**DistServe**

这篇文章是 P/D 解耦方向的代表性基础工作，它指出 Prefill 和 Decode 在计算特征和时延目标上存在明显差异，共置会造成资源竞争，因此将两个阶段部署到不同 GPU 池中，并分别优化资源数量和并行策略

**Mooncake**

Mooncake是在实际生产系统中部署的 KV Cache 中心化 P/D 解耦架构，它不仅分离 Prefill 和 Decode 集群，还利用 GPU 显存、CPU 内存和 SSD 构建分布式 KV Cache 池，并通过全局调度器联合选择 Prefill、Decode 实例和缓存位

**Preble**

Preble主要研究共享前缀场景下，缓存复用和负载均衡之间的冲突。如果始终把相同前缀的请求路由到已有缓存的 GPU，容易造成热点；如果只按照负载均衡路由，又会产生大量重复 Prefill 计算。文章在利用已有前缀缓存和探索低负载节点之间动态选择，并支持热门前缀复制和在线负载重平衡

**FlowKV**

FlowKV主要解决 P/D 解耦后的 KV Cache 传输效率问题

**NetKV**

NetKV 关注运行时应该把 Prefill 生成的 KV Cache 发送到哪个 Decode 实例，仅考虑 Decode 节点负载和前缀缓存命中还不够，还需要考虑 Prefill 与 Decode 节点之间的拓扑距离、链路带宽和实时拥塞情况
